# Cloudflare 前端持久化排期与最小间隔设计

日期：2026-11-09。基线：`18852de`。状态：聊天方案已获同意，详细设计待确认；尚未实现。

## 1. 范围与默认解释

- 在现有仓库管理页，为每个运行目标增加排期编辑：固定时间、随机次数、随机窗口、最小间隔。
- 次数仍为每天计划触发次数，范围 1～24；不是成功次数、累计配额或 GitHub 实际执行次数。
- 所有排期使用 `Asia/Shanghai`，分钟精度，随机窗口不跨日。
- 用户回复同意，但没有明确选择手动间隔范围。本次按最小范围：最小间隔仅约束同一目标的自动触发，手动运行保留现有 30 秒冷却，不消耗自动时段。
- 间隔按 Cloudflare 自动触发请求的本地尝试起点计算，不按 Actions 的排队、开始或完成时间计算。不同目标互不限制。
- 自动请求的 HTTP 失败或结果未知也计入间隔；不能通过超时或未知结果立即重试。
- 不增加数据库、Cron、前端框架、Secrets、浏览器密码存储或 GitHub 状态轮询。
- 本阶段不推送、部署或调用真实订阅、代理、账号、GitHub dispatch、机器人；原有未跟踪复用指南、AGENTS 和规划文件保留。

## 2. 方案选择与配置优先级

选择：现有每目标 Durable Object 保存经过校验的排期覆盖值，Cloudflare 变量作为初值和恢复来源。

- 浏览器本地存储不能支持跨设备、服务端 Alarm 和重部署后的一致执行，不采用。
- 反写 Cloudflare 变量需要额外管理权限并触发部署，且会把账号/令牌配置暴露给编辑流程，不采用。
- 数据库覆盖不改变仓库、工作流、分支、Token 引用、开关或登录配置；只允许编辑排期。

有效排期优先级：身份匹配的数据库覆盖 > `TRIGGER_CONFIG` 内的 `schedule` > 原有每日一次 01:00～23:00 随机默认。

- 页面标明“数据库设置”或“变量配置”，不能把原 JSON 展示成最终生效值。
- 修改变量中的排期不会覆盖已保存的数据库设置；“恢复变量配置”经确认后撤销覆盖。
- 重部署、刷新、换浏览器或设备不清除覆盖。
- 目标身份仍为稳定 id + 仓库/工作流/ref。更换仓库、工作流或分支时，旧覆盖不自动转移；使用新身份的变量初值。
- 变量解析不合法时继续拒绝操作，不借助数据库绕过原配置校验。
- 覆盖记录损坏时失败关闭，显示状态错误，不偷偷回退变量重新开启或重排。

## 3. 排期数据与校验

保留两种现有模式，新增可选 `min_interval_minutes`。变量配置和前端保存共用校验器。

固定模式示例：

```json
{
  "mode": "fixed",
  "times": ["08:30", "13:00", "20:30"],
  "min_interval_minutes": 120
}
```

随机模式示例：

```json
{
  "mode": "random",
  "count": 3,
  "window": {"start": "09:00", "end": "22:00"},
  "min_interval_minutes": 120
}
```

规则：

- 固定列表长度、随机 count 均为 1～24。时间严格为 `HH:mm`，00:00～23:59；固定列表不重复，规范化排序。
- 最小间隔为整数分钟 1～1440；省略为 1，保持旧版不重复分钟的规则。不接受字符串、浮点数、布尔值或空值。
- 默认间隔 1 的规范形式不新增字段，避免旧计划仅因引入默认值而失去绑定或重新随机。
- 固定模式检查相邻时间差，以及每日最后一个时间至次日第一个时间的循环间隔。
- 随机窗口两端包含。设窗口跨度为 end-start，N 为次数，G 为间隔，必须满足 `(N-1)*G <= 跨度` 和 `N*G <= 1440`。
- 例如 09:00～10:00、最小间隔 60 分钟，最多安排两次；三次明确报错，不减少次数、不缩短间隔。
- 只允许对应模式的字段；未知字段、跨日窗口、重复时间、容量不足给出安全字段位置和具体修复建议。
- 固定模式不额外维护 count；随机模式不接受固定 times。窗口仅属于随机模式，避免两套时间限制冲突。

## 4. 随机生成与实际间隔保护

### 计划时间

随机生成不采用反复猜测直到成功的无界重试。复用 Web Crypto 和现有无偏整数抽取，在压缩后的分钟空间选取 N 个不同值并排序，再按位置补回间隔。

设包含两端的分钟数为 L，压缩空间大小为 `L-(N-1)*(G-1)`；排序的抽样值为 y[i]，实际分钟为 `start+y[i]+i*(G-1)`。这保证同日相邻时间至少间隔 G，且仍在窗口内。G=1 与现有无重复分钟抽取等价。

每个目标、每个新计划继续使用新随机数，不引入固定种子。刷新和相同语义的重复保存不重新抽取。

### 真实自动尝试

- 每个目标独立保存最后一次自动尝试时间；不依赖可删除的日志、计划列表或手动 receipts。
- Alarm 即将提交请求前，用持久化时间检查间隔，覆盖跨日、延迟回调和配置修改后的边界。
- 未满足间隔时，该时段标为 `INTERVAL_SKIPPED`，页面解释“最小间隔未到”；不发送 GitHub/机器人请求，不自动补发，也不把它当作成功。
- 不为了凑次数主动推迟固定时间或把随机排期排出窗口。计划次数仍为配置值，实际尝试数可能因 Alarm 延迟、间隔冲突或服务故障而减少，跳过原因必须可见。
- 首次保存间隔不清空已知自动尝试基线；修改间隔、恢复变量、暂停/重开、删除日志、跨日均不清空基线。
- 升级前没有独立的自动基线。仅当旧计划身份与可关联的自动记录可信匹配时恢复；无法确认或记录已删除则标明未建立，不编造历史时间。上线后的每次自动尝试都会建立基线，包括默认间隔为 1 的目标。
- 首个无可信基线的尝试允许执行；保护从可确认基线开始，不声称恢复了已经删除的历史。
- 手动请求不更新自动基线，自动基线也不增加手动限制。现有手动 UUID 幂等和 30 秒冷却不变。

最小间隔不保证 Actions 的实际开始时间；平台排队可能把两个工作流的开始时间拉近。Alarm 延迟也可能使实际请求晚于显示的计划时间，窗口是计划时间约束而不是平台实时执行保证。

## 5. 存储、身份与并发

继续使用原 `SCHEDULES` SQLite 命名空间、导出的 `TriggerSchedule` 及每目标一个 Alarm，不增加类迁移。

每目标增加两条有界记录：

- `schedule_settings`：版本、目标身份 binding、单调递增 revision、覆盖 schedule 或 null。
- `automatic_guard`：版本、目标身份 binding、最后自动尝试时间 last_at。

约定：

- 没有覆盖记录时 revision 为 0、来源为变量。恢复变量写入 schedule:null 的记录并递增 revision，不删除 revision，防止旧标签页再次覆盖新设置。
- 成功写入的 revision 为安全整数；上限时拒绝更新，不循环使用。记录字段、长度、版本和时间均严格校验。
- 保存请求携带页面读取的 revision 和目标 binding。版本冲突返回 `SCHEDULE_CONFLICT`，身份变化返回 `TARGET_CHANGED`，不自动覆盖。
- 相同规范排期不改变已有计划时间；来源变化可以更新元数据，但不会无故抽取新时间。
- 开关 control、手动 receipts、可见 history、会话存储保持独立，不因排期修改而清空。
- 新排期覆盖只保存在该目标数据库中，目标之间不共享可编辑状态。

## 6. 保存、恢复与故障顺序

- 先完整验证请求、配置、身份、revision 和已有状态，再计算有效排期和未来计划，失败不写入。
- 覆盖和新计划通过 SQLite 一次多键 put 或明确事务原子提交；事务内不执行 HTTP、机器人通知或随机重试。
- 之后根据实际数据库开关和 Token 可用性设置/删除 Alarm。关闭或缺 Token 的目标仍可保存排期，但不因保存自动开启或 dispatch。
- 固定模式仍保留今天未来时段，过去时段跳过；随机模式在窗口开始后首次重排为明天完整窗口，保存不立即补发。
- 新排期不重算过去的成功/失败为未运行。若当天已触发，修改后新的未来计划不等于累计配额：不会撤回先前请求，也不保证当日累计请求数等于新次数。
- 重复保存同一语义或重复恢复不额外生成计划；保持 UNKNOWN-before-HTTP 和已有防重复逻辑。
- 自动提交前，slot 的 attempted/UNKNOWN、automatic_guard 和对应 history 检查点原子持久化。持久化失败禁止 HTTP；请求返回后不把 last_at 改成完成时间。
- 原子提交成功但 Alarm 写入失败时返回安全 503/结果未确认；前端重新读取实际 revision/设置，不能声称“完全没保存”。下一次读取/初始化可恢复同一未来 Alarm，不重新随机。
- Alarm 重试始终重新读取覆盖和间隔状态。旧规则的回调不能绕过已提交的新规则，不重试未知请求。
- Cookie 与 CSRF 验证位于现有权限边界；不放宽鉴权、Origin、Content-Type 或 1024 字节请求体上限。

## 7. API 与前端

现有目标列表增加安全字段：有效 schedule、`schedule_source`、`schedule_revision`、`target_binding`、自动基线状态和下一允许自动尝试时间；不返回 Secrets、原始记录或异常。

- `POST /api/admin/targets/<id>/schedule`：保存规范 schedule、revision、binding。
- `POST /api/admin/targets/<id>/schedule/reset`：恢复变量配置，提交 revision、binding。
- 内部目标对象复用对应受保护路由。成功响应返回实际目标状态；校验失败给出安全错误字段与建议。
- `/health` 保留纯变量检查、不读取数据库。配置页明确表格为变量初值；目标卡片和编辑器展示数据库最终值及来源。

界面复用现有目标卡片、三栏目和样式：

- 卡片增加可折叠“排期设置”，有模式选择、随机次数、窗口开始/结束、固定时间增删、最小间隔（分钟）。
- 显示派生的每天次数、来源、保存状态、下一计划时间与跳过原因；不展示另一种模式无关的字段。
- 保存和恢复均为显式操作；恢复需确认。保存不等于运行，不把它复用成手动运行按钮。
- 每目标操作串行，提交期间禁止重复保存。失败保留输入供修改；冲突要求读取新状态后确认，不默默重试覆盖。
- 普通刷新不静默丢弃正在编辑的草稿；草稿只留当前页面内存，不需要浏览器存储。重载恢复已保存值，不保证恢复未保存草稿。
- 所有字段有标签、键盘可达焦点、就地错误和手机布局；时间采用 HTML time 输入但仍由服务端严格校验。
- 12 小时会话、退出撤销、迟到响应隔离、手动 UUID 不确定重试规则全部保留。

## 8. 离线验收与兼容边界

- 默认/旧变量无 override 且间隔为 1：保持已保存排期，不因升级重抽；既有 v1/v2 计划迁移和状态保护继续有效。
- 校验覆盖整数类型、时间、窗口容量、同日/跨日固定间隔、随机每天可行性、未知字段和默认规范形式。
- 随机测试覆盖边界、1/24 次、不重复、最小间隔、G=1 兼容和无偏整数来源；不只测某个幸运抽样。
- 数据库测试覆盖跨实例重启、身份变化、revision 冲突、保存/恢复、相同语义不重抽、关闭和缺 Token 保存。
- 故障测试覆盖原子提交失败、Alarm 写失败、HTTP 前 guard/UNKNOWN 写失败、HTTP 后失败、回调重试、日志删除、跨日和缺失历史基线。
- 浏览器测试覆盖模式切换、校验提示、草稿、Cookie/CSRF、失效会话、迟到响应、双标签页冲突、移动端和键盘。
- 完整 Cloudflare/Python 离线回归、Wrangler dry-run、原生 Workerd/SQLite 重启/原子存储检查；使用虚构值并拦截所有业务外部请求。
- 更新简洁 Cloudflare 指南，清楚区分变量初值、数据库覆盖、计划次数与实际尝试、自动间隔与手动冷却。
- 旧 `18852de` 不认识覆盖/间隔保护；直接降级可能忽略数据库设置。回退需要停用目标并兼容处理，不能清空数据库解决。
