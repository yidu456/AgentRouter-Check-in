# Cloudflare 多次排期、持久登录与配置检查设计

日期：2026-11-08。基线：`1f08af5`。状态：详细设计待用户确认，尚未实现。

## 1. 范围与默认规则

- 次数按**每个运行目标每天的计划触发次数**计算，不是累计总次数，也不是签到成功次数。
- 运行目标仍是仓库 + 工作流 + 分支；同一组合不能重复配置。增加次数通过目标内的排期配置完成。
- 所有时间使用 `Asia/Shanghai`，精度为分钟。不修改 GitHub Actions 的等待策略或签到逻辑。
- 支持固定时间列表和指定窗口内随机多次；不做跨日窗口、按周排期、累计配额或后台在线编辑 JSON。
- 刷新保留登录；会话固定有效期 12 小时，不因刷新无限续期。
- 保留仓库管理 / 配置检查 / 运行日志三个栏目、现有开关和手动运行规则。
- 没有 `schedule` 的旧 JSON 保留每日一次、01:00～23:00 随机及已有首次排期规则。

### 方案选择

推荐每日次数：与现有“每天独立随机”模型一致，无需额外的累计配额状态。累计 N 次后停止是另一种配额功能，本次不叠加。

登录选择安全 Cookie + 服务端会话记录，而不是把密码或 Basic 凭据保存到浏览器存储。仅签名、无撤销记录的 Cookie 无法可靠撤销单个已复制会话，因此保留有界服务端会话记录。

## 2. 排期配置

`TRIGGER_CONFIG` 顶层继续使用 `version: 1`，每个 target 增加可选 `schedule`。现有字段及默认 `enabled: true` 不变。

固定时间：每天三次，次数由列表长度决定，不额外设置重复的 count。

```json
{
  "id": "repository_a",
  "repository": "owner/AgentRouter-Check-in",
  "workflow": "Checkin.yml",
  "ref": "main",
  "token_secret": "GITHUB_TOKEN_A",
  "schedule": {
    "mode": "fixed",
    "times": ["08:30", "13:00", "20:30"]
  }
}
```

随机多次：每天在窗口内独立抽取三次，保存排序后的实际时间。

```json
{
  "id": "repository_b",
  "repository": "other/AgentRouter-Check-in",
  "workflow": "Checkin.yml",
  "ref": "main",
  "token_secret": "GITHUB_TOKEN_B",
  "schedule": {
    "mode": "random",
    "count": 3,
    "window": {"start": "09:00", "end": "22:00"}
  }
}
```

校验：

- 固定列表长度、随机 count 均为 1～24；count 必须是整数，不接受字符串或布尔值。
- 时间严格为 `HH:mm`，范围 00:00～23:59。固定列表不允许重复，解析后排序。
- 随机窗口 start 不晚于 end，两端包含；count 不大于窗口内可选分钟数。相同起止时间仅允许一次。
- 随机抽取使用现有 Web Crypto 来源，分钟不重复，日期和目标之间独立；不使用 Math.random 或固定种子。
- mode 决定允许的字段：fixed 只接受 times；random 只接受 count/window。错误给出安全字段位置与修复建议。
- 配置只在 Cloudflare Variables & Secrets 中修改并发布。管理页展示，不增加第二套数据库排期编辑来源。

## 3. 排期存储与执行

继续使用每目标一个 Durable Object、一个 Alarm。Alarm 指向最早待执行时段，完成后设置下一时段，不增加轮询 Cron。

### 存储边界

- 增加 version 2 的多时段计划，保存日期、计划身份和排序后的 slots。
- 每个 slot 保存时间、处理状态、结果及对应历史记录 ID；没有与 slots 重复维护的可漂移索引计数。
- 仓库身份继续用于开关与手动请求幂等记录；计划身份另包含规范化 schedule，避免修改排期重置已关闭的目标。
- 历史记录、手动请求防重复记录及现有开关不删除；日志仍按目标最多保留 20 条。
- 接受已有 version 1 计划。未修改旧排期的目标保留原来保存的随机时间与 attempted 状态，再转换为单 slot 计划，不重新抽取。
- 新版写入 v2 后，直接部署旧代码不保证能读新计划；回退前需要兼容处理，不能清空数据库“修复”。

### 初次排期与配置变化

- 省略 schedule 的旧目标完全保留现有日期选择规则。
- 显式 random 排期：窗口开始前可为今天生成完整计划；开始后首次初始化为明天生成完整计划，避免部署时突发补发。
- 显式 fixed 排期：今天尚有未来时间时保留这些时段，已过去的时段标为跳过；今天没有未来时间则排明天。
- 关闭删除 Alarm，不删除计划。重新开启只恢复未来时段，不补发暂停期间已过的时段。
- 改排期使旧计划失效，不补发旧时间；新规则按初次排期规则生成未来计划。开关覆盖仍保留。
- 刷新保留已保存时间。缺失的有效未来 Alarm 按原时间恢复，不重新随机。
- 缺失 Token、配置非法、目标删除或存储损坏仍失败关闭，不借其他目标配置。

### 防重复与延迟

- 每次 HTTP 前先持久化当前 slot 的 attempted/UNKNOWN 和历史记录，保留现有不确定交付不重发原则。
- Alarm 重复回调、进程重启或回调重试不能再次提交已处理 slot。
- 普通同日回调延迟可以执行该到期 slot；若延迟跨过多个时段，只处理最近一个到期时段，较早积压标为跳过，不集中补发。
- 跨日期的过期时段全部跳过；刷新和管理操作绝不直接提交已到期任务。
- 手动运行不消耗自动时段，不改变自动计划；现有 UUID 幂等和 30 秒冷却保留。
- 调度次数只表示计划/尝试提交次数。GitHub 拒绝、排队、取消、响应未知或签到失败不保证补足成功次数。
- 企业微信保留每次触发通知；明确“GitHub 已受理”不等于 Actions 完成或签到成功。

## 4. 刷新保留登录

复用现有 `DEBUG_ACCESS_TOKEN` 入口与 `ADMIN_USERNAME` / `ADMIN_PASSWORD`。不增加用户必填 Secret，不把隐藏路径当作认证。

### 浏览器协议

- 增加登录、查询当前会话、退出三个专用 API。
- 登录使用现有 Basic 凭据验证，通过后签发新随机会话；表单字段和 JS 内的 Basic 凭据立即清除。
- Cookie 使用 `__Host-` 前缀、`Secure; HttpOnly; SameSite=Strict; Path=/`，有效期 12 小时；不设置 Domain。
- Cookie 包含有界、版本化的随机 nonce、过期时间及 HMAC，不包含用户名密码、GitHub Token 或其他配置值。
- HMAC 使用 Web Crypto。签名密钥由服务端生成并持久保存，不直接使用管理密码作为签名密钥，也不新增用户必填 Secret。签名绑定请求主机与由服务端密钥计算的当前管理凭据/入口身份标签；修改密码、用户名或入口值后旧会话失效。
- 页面启动先通过同源查询恢复会话；有效时直接显示管理页，无效时显示登录表单。JS 不读取 Cookie，也不使用 localStorage/sessionStorage 保存认证。
- 会话查询返回到期时间和 CSRF 令牌，不返回 Cookie、密码或签名密钥。
- Cookie 认证的写操作要求同源 Origin、JSON 及匹配的 CSRF 令牌。没有正确令牌不能触发、开关、删日志或退出。
- 保留原 Basic API 认证，供已有 CLI 和内部调用兼容；不能用缺失/无效 Cookie 绕过原认证检查。

### 服务端会话与撤销

- 复用 SCHEDULES 绑定，使用与 `v1:<target id>` 不相交的独立会话对象名称；认证存储处理抽到独立模块，不混进目标排期状态。
- 每个活跃记录只保存会话摘要及过期时间，不保存原始 Cookie、管理密码。服务端签名密钥作为会话对象的独立私有元数据保存，绝不出现在响应、日志、配置展示或逐会话记录中；缺失时只在创建首个会话前生成，损坏时失败关闭，不静默重建。
- 活跃记录最多 128 条；新登录清理已过期记录，到达容量拒绝继续创建，不无限增长或驱逐仍有效会话。
- Cookie 签名和过期检查通过后，还必须找到对应活跃记录；存储故障失败关闭。
- 主动退出撤销当前记录，再清除 Cookie；复制出的同一 Cookie 随之失效，其他独立会话不受影响。
- 撤销失败明确提示，不能假称服务端已经退出；不把刷新/pagehide当作主动撤销。
- 不新增会话轮询 Alarm，不改变仓库 Alarm。保留 HTTPS、no-store、无跨域授权及现有 CSP。

## 5. 直观配置检查

延续现有配色、字体和三栏结构，不引入外部 UI 框架、远程字体或图表依赖。

```text
配置检查
  JSON 配置       GitHub 凭据       数据库绑定       企业微信
  通过 / 错误     已填写 / 缺失     已绑定 / 缺失    已填写 / 未配置

  仓库               工作流 / 分支      排期       每天次数    时间 / 窗口    Token
  owner/repo         Checkin.yml/main   固定       3           时间标签       已填写
  other/repo         Checkin.yml/main   随机       3           09:00～22:00   缺失

  错误：第 2 个目标的 schedule.count
  修复：填写 1～24 的整数，且不超过窗口分钟数
  [展开技术诊断]
```

- 状态同时使用图标、短标签和颜色，不能只靠红/绿区分；支持手机布局及键盘操作。
- Token 的“已填写”仅代表存在/格式校验，不写“权限已验证”。数据库绑定不等于数据库健康，机器人格式正确不等于送达成功。
- 表格展示安全的仓库/工作流/分支/模式/次数/时间标签/Secret 名称状态，不显示任何 Secret 值。
- JSON 语法损坏时显示无法解析，不虚构零目标或有效行。结构可解析但某字段错误时，仅展示逐字段校验通过的值，非法值显示占位，突出目标序号和字段。
- 展示复用同一配置校验规则，严格执行配置解析仍失败关闭，不能因部分行有效就运行这些行。
- 技术细节折叠且只含白名单字段/错误码，不展示原始 JSON、异常字符串或非法字段值。
- 仓库管理显示实际下一次时间及已保存时段列表；明确区分已处理、已跳过、GitHub 已受理和结果未知，不把跳过计作成功触发。
- 运行日志继续只放日志栏，按仓库分类。配置页不混入历史日志或手动触发按钮。

## 6. 验收与交付边界

- 用现有 Node 测试与离线存储/fetch fixture 做 TDD；不安装新测试框架。
- 配置测试覆盖默认兼容、固定/随机边界、重复分钟、跨日拒绝、count 类型和安全诊断。
- 排期测试覆盖多次执行、独立随机、刷新不重抽、v1 时间迁移、开关与排期变化、重复 Alarm、写失败重启、延迟跳过、手动不占自动次数。
- 会话测试覆盖刷新/重载恢复、Cookie 属性、篡改/过期/跨主机/凭据轮换、退出撤销、CSRF、存储失败和敏感值不泄露；Basic 兼容测试保留。
- 前端测试覆盖卡片、错误定位、折叠诊断、有效/损坏配置、未知权限、手机布局和退出/并发响应的隔离。
- 完整 Python/Cloudflare 回归、Wrangler dry-run 和 UI 离线可视检查；没有真实签到、GitHub dispatch 或机器人发送。
- 不改 Python 账号配置、随机池快照、指纹/余额逻辑；不添加 Actions 等待或删除旧 Cron。
- 代码实施、推送和实际部署分别记录；设计确认不能被当作线上效果已经验证。

参考：Cloudflare 官方文档确认每个 Durable Object 只有一个 Alarm，任务需要持久化并保持重复回调安全；本项目继续使用原生 Alarm，不引入 Agents SDK 或另一套调度服务。
